AI 代码开发平台 MVP 需求规格说明书

本文档定义 AI 代码开发平台第一版 MVP 的产品范围、用户角色、核心流程、功能需求、页面要求、AI 输出要求、验收标准和非功能要求。 它承接《AI 代码开发平台设计方案》，用于把总体方案收敛成可排期、可评审、可开发、可验收的第一版需求。

文档类型：MVP 需求规格 版本：v0.1 状态：草案 适用阶段：立项评审 / MVP 开发前
1. 文档目的 2. MVP 定位 3. 用户角色 4. 范围定义 5. 核心用户旅程 6. 阶段流程 7. 功能需求 8. 页面与交互需求 9. AI 输出要求 10. 权限与审批 11. 非功能需求 12. MVP 验收标准 13. 风险与依赖 14. 里程碑建议

1. 文档目的

本需求规格说明书用于明确 AI 代码开发平台 MVP 版本的建设边界，避免第一版同时追求过多能力而导致周期失控。

MVP 核心目标： 第一版必须打通“上传项目 - 上传需求 - AI 生成澄清问题 - 业务反馈 - 方案生成 - 详细设计生成 - AI 编码 - 自测 - CR”的最小闭环。

本文档不包含最终数据库表结构、详细接口字段、完整 UI 视觉稿、全部 Agent 提示词、生产级部署细节。这些内容应在后续《产品原型说明》《MVP 技术详细设计》《Agent 设计文档》《测试与验收方案》中展开。

2. MVP 定位

要证明什么

  • AI 能结合项目代码和需求文档发现不明确问题。
  • 多轮澄清后，AI 能判断是否具备开发条件。
  • AI 能生成可评审的方案和详细设计。
  • AI 能在受控范围内修改代码，并通过测试和 CR 闭环。

第一版不追求什么

  • 不追求完整替代企业 DevOps 平台。
  • 不追求所有语言和框架一次性支持。
  • 不追求复杂多 Agent 全自动并行开发。
  • 不追求生产级插件市场、计费系统和组织级知识库。

成功标志

  • 可在真实中小型项目上跑通端到端流程。
  • AI 生成的问题和设计能被业务与研发确认有价值。
  • AI 代码变更可被追溯、测试、审查和回滚。
  • 平台流程稳定，不因单个 AI 任务失败导致整体不可用。

3. 用户角色

角色 核心诉求 MVP 权限
平台管理员 管理用户、项目、模型配置、沙箱策略和权限。 创建项目、配置模型、管理成员、查看审计。
项目负责人 推进需求从澄清到代码合并，控制范围和风险。 创建工作流、推进阶段、审批回滚、确认最终交付。
业务确认人 回答 AI 提出的问题，确认业务规则和验收标准。 查看需求问题、填写业务反馈、确认澄清结论。
架构师 / 技术负责人 审查方案设计、详细设计、关键技术风险。 审批方案、审批详细设计、驳回高风险设计。
开发者 查看 AI 改动，人工接管代码，处理冲突和补充实现。 查看代码、编辑代码、查看 Diff、接管 Agent 任务。
测试 / 质量负责人 确认测试矩阵、查看自测结果、审查质量风险。 查看测试报告、审批测试豁免、补充验收条件。
只读审计人员 追溯 AI 决策、代码变更、审批和测试证据。 只读查看项目、工作流、审计日志和阶段产物。

4. 范围定义

MVP 范围内

范围 说明 优先级
项目上传与代码工作台 支持 ZIP 上传或 Git 地址导入，展示文件树、代码内容、编辑、保存、Diff。 必须
需求文档上传与解析 支持 Markdown、TXT、PDF、Word 至少一种结构化解析方式；MVP 推荐优先 Markdown/TXT/PDF。 必须
AI 需求问题生成 AI 结合需求文档和项目代码，生成不明确问题、原因、影响范围和优先级。 必须
澄清闭环 支持录入业务反馈，AI 归纳答案，判断是否继续追问或进入方案阶段。 必须
方案和详细设计生成 AI 生成方案设计和详细设计，至少覆盖影响范围、实现方式、文件计划、测试计划。 必须
单 Agent 代码编写 MVP 优先支持单 Agent 在独立分支或工作区中生成代码变更。 必须
基础自测 支持配置并运行构建、单测、Lint 命令，展示日志和结果。 必须
基础 CR AI 对最终 Diff 做正确性、设计一致性、可维护性、安全性初步审查。 必须
阶段反思 每个阶段生成反思报告，判断是否可进入下一阶段。 必须
有限多 Agent 策略 MVP 只要求能识别是否适合多 Agent，并生成分工建议；不要求复杂并行执行。 应该

MVP 范围外

  • 复杂多 Agent 自动并行开发、跨仓库协作和自动冲突修复。
  • 企业级计费、租户套餐、插件市场、外部生态集成。
  • 全语言全框架支持；第一版优先选择团队最熟悉的 1-2 类项目。
  • 生产级私有化部署、跨区域容灾和大规模多租户运营能力。
  • 自动上线发布；MVP 只做到可合并代码和交付报告。

5. 核心用户旅程

项目负责人创建项目
  → 上传代码项目
  → 平台解析项目结构并生成项目画像
  → 上传需求文档
  → AI 生成需求不明确问题
  → 业务确认人填写反馈
  → AI 继续追问或判断可开发
  → 架构师审查 AI 生成的方案设计
  → AI 生成详细设计和任务计划
  → 编码 Agent 修改代码
  → 平台运行自测
  → 测试失败则回流给 Agent 修复
  → CR Agent 审查代码
  → 项目负责人确认最终交付产物

6. 阶段流程

阶段 用户动作 AI / 系统动作 阶段产物 通过条件
项目导入 上传 ZIP 或填写 Git 地址，选择项目类型。 解析目录、识别语言框架、生成文件摘要和测试命令建议。 代码树、项目画像、索引状态。 项目可浏览，关键文件可读取。
需求分析 上传需求文档，确认需求版本。 结合项目代码生成不明确问题和风险点。 问题清单、风险清单。 问题包含原因、影响范围和优先级。
澄清阶段 填写业务反馈，确认 AI 归纳是否正确。 合并答案，检查矛盾，继续追问或判断可开发。 澄清记录、决策记录。 无阻断级未知项。
方案生成 选择生成方案，评审方案。 生成技术路线、影响范围、Agent 策略、风险和回滚建议。 方案设计文档。 架构师或技术负责人确认。
详细设计 确认接口、数据、流程、测试要求。 生成详细设计、文件修改计划和测试矩阵。 详细设计文档、任务计划。 任务输入输出明确，可进入编码。
代码编写 触发 Agent 编码或人工接管。 在独立工作区修改代码，生成 Diff 和说明。 代码变更、实现说明。 代码可保存，Diff 可查看。
自测修复 选择测试命令，查看测试报告。 运行构建、测试、Lint，失败则归因并修复。 测试报告、修复记录。 阻断级测试通过或人工确认豁免。
代码 CR 查看 CR 问题，确认是否修复或豁免。 审查 Diff，输出问题和优化建议。 CR 报告、最终交付摘要。 高优先级问题清零或有审批豁免。

7. 功能需求

编号 功能 需求描述 优先级
FR-001 项目创建 用户可以创建项目，填写项目名称、描述、技术栈、代码来源。 必须
FR-002 项目上传 支持上传 ZIP 包；可选支持 Git 地址导入。上传后展示解析进度。 必须
FR-003 代码树展示 展示项目目录树，支持展开、搜索、打开文件。 必须
FR-004 代码查看与编辑 支持代码高亮、编辑、保存、只读/编辑模式切换。 必须
FR-005 Diff 查看 展示 AI 或人工修改前后的文件差异，支持按文件查看。 必须
FR-006 需求文档上传 支持上传需求文档，保存版本，展示解析后的文本内容。 必须
FR-007 需求问题生成 AI 根据需求和项目上下文生成不明确问题、候选答案、影响范围和优先级。 必须
FR-008 业务反馈录入 用户可以逐条填写业务答案，AI 自动归纳为澄清记录。 必须
FR-009 澄清循环 AI 判断是否还需要继续提问；如有阻断问题则继续生成问题。 必须
FR-010 阶段反思 每个阶段完成后生成反思报告，包含完整性、准确性、一致性、风险和下一步建议。 必须
FR-011 方案设计生成 AI 生成方案设计，包括目标、影响范围、技术路线、风险、回滚、Agent 策略。 必须
FR-012 详细设计生成 AI 生成详细设计，包括文件修改计划、接口、数据、流程、异常、测试矩阵。 必须
FR-013 AI 编码 AI 根据详细设计修改代码，生成 Diff、实现说明和待验证点。 必须
FR-014 自测执行 支持运行预设构建、测试、Lint 命令，并展示日志和结果。 必须
FR-015 失败修复回流 测试失败时，AI 分析原因并生成修复建议或直接修复。 必须
FR-016 代码审查 AI 审查最终 Diff，输出问题、优先级、建议和是否阻断合并。 必须
FR-017 审批记录 关键阶段支持人工通过、驳回、退回修改和备注。 应该
FR-018 追溯链展示 支持从代码变更追溯到需求、澄清、设计、测试和 CR 结论。 应该
FR-019 上下文包记录 记录 AI 每次调用使用的需求、代码、设计和模型版本。 应该
FR-020 工作流时间线 展示每个阶段的状态、产物、耗时、审批和失败记录。 应该

8. 页面与交互需求

页面 核心内容 关键操作
项目列表页 项目名称、状态、最近工作流、创建人、更新时间。 创建项目、进入项目、删除或归档项目。
项目上传页 代码来源、上传进度、解析状态、项目画像。 上传 ZIP、填写 Git 地址、重新解析、确认项目根目录。
代码工作台 文件树、代码编辑器、Diff、搜索、工作流侧栏。 打开文件、编辑保存、查看 Diff、人工接管。
需求分析页 需求文档、AI 问题清单、影响范围、优先级。 上传文档、触发分析、选择问题、导出问题。
澄清页 问题、业务反馈、AI 归纳、冲突提醒、澄清历史。 填写答案、确认归纳、继续追问、进入方案阶段。
方案设计页 技术方案、影响模块、风险、Agent 策略。 生成方案、重新生成、审批通过、驳回修改。
详细设计页 文件计划、接口设计、流程设计、测试矩阵。 生成详细设计、评论、审批、生成开发任务。
编码与 Diff 页 Agent 任务、代码变更、实现说明、待验证点。 触发编码、查看 Diff、接受/拒绝变更、人工编辑。
自测页 测试命令、运行日志、失败原因、修复建议。 运行测试、查看日志、触发修复、标记环境问题。
CR 页 审查问题、优先级、文件位置、优化建议。 触发 CR、修复问题、豁免、生成最终交付报告。

9. AI 输出要求

MVP 所有关键 AI 输出都必须结构化保存，避免只保存聊天文本导致后续无法追溯、校验和自动流转。

输出类型 必填内容 校验要求
需求问题 问题、分类、优先级、为什么要问、影响范围、候选答案。 阻断级问题必须有原因和影响说明。
澄清归纳 业务答案摘要、决策记录、是否存在冲突、是否继续追问。 必须引用原始业务反馈。
反思报告 阶段评分、是否可继续、阻断问题、非阻断问题、证据链。 阻断问题未关闭时不能自动进入下一阶段。
方案设计 目标、范围、技术路线、影响模块、风险、回滚、Agent 策略。 必须说明为什么选择当前方案。
详细设计 文件计划、接口、数据、流程、异常、测试矩阵。 每个开发任务必须有输入、输出和验收条件。
代码变更说明 修改文件、修改原因、实现方式、风险、测试建议。 每个变更必须关联详细设计任务。
测试报告 命令、耗时、状态、失败日志、原因归纳、修复建议。 环境失败和代码失败必须区分。
CR 报告 问题、严重级别、文件位置、原因、建议、是否阻断。 高优先级问题必须修复或审批豁免。

10. 权限与审批

动作 允许角色 MVP 规则
创建项目 平台管理员、项目负责人 创建人默认成为项目负责人。
上传需求 项目负责人、业务确认人 上传后生成新需求版本。
填写业务反馈 业务确认人、项目负责人 反馈必须保留填写人和时间。
审批方案 架构师、技术负责人 不通过则退回方案生成阶段。
触发 AI 编码 项目负责人、开发者 详细设计未通过时禁止触发。
人工编辑代码 开发者、项目负责人 人工编辑后必须重新生成 Diff 和测试建议。
CR 豁免 技术负责人、质量负责人 必须填写原因和到期时间。
确认最终交付 项目负责人 必须已完成自测和 CR。

11. 非功能需求

类别 要求
稳定性 AI、索引、测试、CR 等长任务必须异步执行；任务失败不能影响用户继续浏览项目。
性能 中小型项目文件树首屏加载应在可接受时间内完成；长任务必须展示进度。
安全 上传项目必须进行密钥扫描；代码执行必须在沙箱中进行；敏感信息不得传入模型上下文。
可追溯 每个阶段产物必须记录输入来源、输出结果、执行人或 Agent、时间和版本。
可恢复 工作流失败后应允许重试、退回、人工接管或取消。
兼容性 MVP 优先支持主流浏览器和一种团队主要技术栈项目。
可用性 所有阶段必须展示当前状态、下一步动作和阻断原因。

12. MVP 验收标准

端到端验收

  • 使用一个真实中小型项目，可以完成项目上传、需求上传、需求问题生成、业务反馈录入、方案生成、详细设计生成、AI 编码、自测、CR 的完整流程。
  • AI 生成的问题至少包含问题原因、影响范围、优先级和候选答案。
  • 澄清阶段可以多轮循环，并能明确判断是否可进入方案阶段。
  • 方案和详细设计可被人工审批、驳回和重新生成。
  • AI 代码变更可以在 Diff 中查看，并能关联到详细设计任务。
  • 测试失败可以生成失败原因和修复建议，修复后可重新测试。
  • CR 报告能识别至少正确性、可维护性、安全性、设计一致性四类问题。
  • 最终交付报告能展示需求、澄清、设计、代码、测试、CR 的链路。

质量验收

指标 MVP 验收口径
需求问题有效性 业务确认人认为 AI 问题中至少一半具有实际澄清价值。
流程可完成性 至少 3 个不同需求样例可以跑通端到端流程。
代码可审查性 AI 生成的每个代码变更都能在 Diff 中查看并人工接管。
失败可恢复性 AI 输出失败、测试失败、审批驳回均能停在明确状态并继续处理。
审计完整性 关键用户操作、AI 阶段产物、审批和测试结果都有记录。

13. 风险与依赖

风险 影响 应对策略
AI 对代码理解不准确 生成错误问题、错误方案或错误代码。 引入代码索引、证据链、反思报告和人工审批。
项目环境不可复现 测试无法运行，代码质量无法验证。 要求维护项目环境声明，优先支持可稳定构建的项目。
需求文档质量差 AI 澄清问题过多或偏离重点。 支持多轮澄清，允许人工补充业务背景。
第一版范围过大 开发周期不可控。 严格限制 MVP 范围，多 Agent 并行、企业级插件等放到后续版本。
沙箱执行安全风险 上传代码可能包含恶意脚本。 默认受限容器执行，限制网络、资源和凭证。

14. 里程碑建议

里程碑 交付内容 验收重点
M1：项目工作台 项目创建、上传、代码树、代码查看、编辑、Diff。 真实项目可导入、查看和修改。
M2：需求澄清闭环 需求上传、AI 问题生成、业务反馈、澄清循环、反思报告。 AI 能提出有效问题并判断是否可开发。
M3：方案与详细设计 方案生成、详细设计生成、审批、任务计划。 设计能指导代码修改。
M4：AI 编码与自测 Agent 编码、Diff、测试运行、失败修复回流。 能完成小需求代码修改并通过测试。
M5：CR 与交付报告 AI CR、问题修复、追溯链、最终交付报告。 交付结果可审查、可追溯、可回滚。
推荐开发策略： 先完成 M1 和 M2，尽快验证“AI 结合代码生成需求澄清问题”的核心价值；确认价值后再进入代码生成和 CR 能力建设。
