AI 代码开发平台设计方案

面向“需求澄清 - 方案设计 - 详细设计 - 代码编写 - 自测修复 - 代码审查优化”的端到端智能研发平台。 核心目标是让 AI 在可控、可追溯、可复盘的流程中完成研发协作，同时保留业务确认、架构评审和代码质量门禁。

1. 建设目标

业务目标

  • 把业务需求转化为可开发、可验证、可追溯的工程任务。
  • 减少需求不清导致的返工，让 AI 主动识别规则、边界、定义、异常场景和验收口径中的缺口。
  • 让业务、产品、架构、开发、测试、代码审查都能围绕同一条上下文链路协作。

工程目标

  • 支持上传完整项目，并提供类似 VS Code 的代码树、搜索、编辑、Diff、提交和回滚能力。
  • 支持 AI 基于代码仓库、需求文档、澄清记录、方案设计和详细设计进行代码开发。
  • 支持单 Agent 和多 Agent 自动切换，复杂任务可拆分并行开发、独立自测、统一集成。

质量目标

  • 每个阶段都有反思报告，检查准确性、一致性、完整性、风险和是否可进入下一阶段。
  • 所有 AI 结论都要有证据来源，例如需求文档片段、代码文件、接口定义、测试结果。
  • 所有代码变更进入独立分支或工作区，经过测试、审查和质量门禁后才允许合并。
推荐原则： AI 不直接“跳到写代码”，而是通过可审计的阶段流转逐步收敛不确定性。平台的核心价值不是替代研发流程，而是让研发流程更清晰、更快、更少返工。

2. 总体架构

平台建议采用前后端分离、事件驱动、任务队列、沙箱执行、可观测的分层架构。AI 相关能力不直接散落在业务接口中，而是统一通过 AI 编排服务调用，便于模型切换、提示词版本管理、成本控制和结果审计。

后端 API Java Spring Boot / Node.js NestJS / Go 根据团队技术栈选择。核心要求是接口稳定、任务异步化、权限和审计完善。

AI 编排 Agent Orchestrator + Prompt Registry + JSON Schema 校验 集中管理模型调用、上下文组装、工具调用、结果校验、重试和降级。

执行环境 Docker / Kubernetes Job / Firecracker 或受限容器 运行测试和构建必须隔离，避免项目代码影响平台稳定性与安全性。

3. 研发流程设计

平台主流程采用“阶段状态机 + 反思门禁 + 人工确认”的方式。AI 可以推进任务，但关键阶段必须产出结构化结果，并由平台判断是否满足进入下一阶段的条件。

项目导入上传 ZIP 或拉取 Git，生成代码索引。
→
需求分析AI 识别不明确点，生成业务问题。
→
澄清循环录入业务反馈，继续追问直到可开发。
方案生成生成技术方案、架构方案、Agent 策略。
→
详细设计生成接口、数据、流程、异常、测试设计。
→
代码编写单 Agent 或多 Agent 分工实现。
代码自测构建、单测、集成检查、静态扫描。
→
整改优化失败项回流给对应 Agent 修复。
→
代码 CR审查问题、优化建议、最终合并。

4. 阶段反思机制

每个阶段完成后都必须进入反思阶段。反思不是简单总结，而是一个质量门禁：判断当前阶段是否准确、完整、一致、可追溯，是否能进入下一阶段。

关键设计： 反思 Agent 必须与执行 Agent 隔离。执行 Agent 负责产出，反思 Agent 负责质疑、校验和打分，避免同一个 Agent 自我确认导致遗漏。

统一反思维度

维度 检查内容 不通过示例
完整性 输入是否覆盖、产出是否缺少关键部分、是否有未处理的边界条件 需求只覆盖正常流程，没有异常、权限、兼容性和验收条件
准确性 结论是否被需求文档、代码、测试或人工确认支持 AI 假设已有接口存在，但代码库中没有对应实现
一致性 需求、澄清、方案、详细设计、代码之间是否冲突 澄清要求兼容旧数据，方案却要求强制迁移并删除旧字段
可执行性 是否能拆成具体任务，是否有明确输入输出和完成标准 “优化性能”没有指标、范围、基线和验收口径
风险 是否识别安全、性能、数据、兼容性、上线回滚风险 涉及支付逻辑但没有幂等、审计、异常补偿说明
证据链 每个关键判断是否能追溯到文档、代码、日志、测试结果或人工确认 方案声称“影响很小”，但没有列出影响文件和调用链

阶段门禁规则

  • 阻断存在关键业务规则不清、数据口径冲突、接口入参出参不明、测试环境不可用时，不允许进入开发。
  • 可延后非核心体验优化、低风险日志补充、非阻断性能建议可进入后续阶段，但必须进入待办清单。
  • 通过输入完整、结论有证据、方案可执行、风险有处理策略时允许自动流转或提交人工确认。

5. Agent 编排设计

平台不是简单调用一个聊天模型，而是由 AI 编排服务根据阶段、任务复杂度、代码影响面和风险自动选择单 Agent 或多 Agent 模式。

Agent 角色

Agent 职责 主要输入 主要产出
需求分析 Agent 识别需求不明确点、生成业务问题、维护澄清闭环 需求文档、项目画像、历史澄清 问题清单、追问建议、可开发性判断
架构方案 Agent 生成技术方案、架构变更、任务拆分和风险策略 需求、澄清、代码依赖图 方案设计、Agent 策略、任务 DAG
详细设计 Agent 编写接口、数据、流程、异常、测试设计 方案设计、代码结构、接口规范 详细设计文档、验收标准、测试矩阵
编码 Agent 按任务实现代码，提交 Patch，说明影响范围 详细设计、局部代码上下文、任务约束 代码变更、实现说明、待验证点
测试 Agent 运行测试、补充测试、定位失败、反馈修复建议 代码变更、测试设计、测试日志 测试报告、失败原因、修复任务
代码审查 Agent 检查缺陷、安全、性能、可维护性和设计一致性 Diff、详细设计、测试报告 CR 问题、优化建议、优先级
集成 Agent 合并多 Agent 产物，处理冲突，统一风格和提交说明 各编码 Agent 分支、任务 DAG、测试结果 集成分支、冲突处理报告、最终变更摘要
反思 Agent 对每个阶段做质量评估，判断是否可进入下一阶段 阶段输入、阶段产出、证据链 反思报告、阻断问题、下一步建议

单 Agent / 多 Agent 判断规则

判断条件 单 Agent 多 Agent
代码影响范围 1-3 个文件、单模块、低耦合 多模块、多服务、多语言或跨端联动
业务复杂度 规则简单、无复杂状态流转 规则多、状态机复杂、强一致性或金融类场景
风险等级 低风险功能、可快速回滚 涉及权限、支付、数据迁移、安全、性能瓶颈
并行收益 任务前后依赖强，并行价值低 前端、后端、测试、文档、迁移可并行
测试要求 单元测试即可覆盖主要逻辑 需要集成测试、回归测试、契约测试或压测

多 Agent 执行策略

  1. 由架构方案 Agent 把需求拆成任务 DAG，明确每个任务的输入、输出、依赖和验收标准。
  2. 每个编码 Agent 在独立工作区或分支中完成自己的任务，禁止直接修改主分支。
  3. 测试 Agent 对每个分支进行局部测试，再对集成分支进行全量测试。
  4. 集成 Agent 负责合并 Patch、处理冲突、统一代码风格和提交说明。
  5. 代码审查 Agent 对最终 Diff 做审查，问题按优先级回流给对应 Agent。

6. 核心功能模块

6.1 项目上传与代码工作台
  • 支持 Git 地址导入、分支选择、ZIP 上传、项目版本快照。
  • 支持类似 VS Code 的文件树、代码打开、多标签页、全文搜索、符号搜索、跳转定义、引用查找。
  • 支持在线编辑、保存、格式化、Diff 查看、提交、回滚、分支切换。
  • 支持只读模式、AI 修改模式、人工接管模式。
  • 上传后自动执行密钥扫描、依赖识别、语言识别、入口识别、测试命令推断。
6.2 需求文档中心
  • 支持上传 Word、PDF、Markdown、图片 OCR、接口文档、Excel 规则表。
  • 文档解析后保留原文位置，AI 结论必须引用来源片段。
  • 需求版本化管理，每次更新文档都触发差异分析，标记受影响问题、方案和代码任务。
  • 需求问题按类型分类：业务规则、字段定义、权限、异常、兼容性、验收、非功能需求。
6.3 澄清闭环模块
  • AI 自动生成问题清单，每个问题包含问题背景、为什么要问、影响模块、候选答案、优先级。
  • 业务反馈录入后，AI 自动归纳为决策记录，并检查是否与已有需求或历史答案冲突。
  • 支持多轮澄清，直到反思 Agent 判断没有阻断级未知项。
  • 所有澄清记录进入后续方案、详细设计、代码开发和 CR 的上下文。
6.4 方案生成模块
  • 输出目标、范围、影响模块、技术路线、架构变化、数据变化、接口变化、风险和回滚策略。
  • 给出单 Agent 或多 Agent 实现建议，并说明原因。
  • 生成任务拆分和依赖关系，供后续详细设计和代码任务使用。
  • 支持方案对比，例如“最小改动方案”“可扩展方案”“性能优先方案”。
6.5 详细设计文档模块
  • 生成完整详细设计：模块设计、接口设计、数据结构、状态流转、异常处理、日志审计、测试设计。
  • 详细设计必须和代码结构绑定，明确要改哪些文件、可能新增哪些文件、调用链如何变化。
  • 支持人工评论、局部重写、版本对比和批准流程。
  • 生成开发任务卡，每张任务卡可直接分配给编码 Agent。
6.6 代码编写与变更管理
  • AI 修改代码前先生成修改计划，包括文件列表、修改原因、风险点和测试策略。
  • 所有代码写入独立分支或工作区，平台保留 Patch、提交说明和 Agent 执行日志。
  • 支持按任务查看 Diff，支持人工接受、拒绝或编辑 AI 变更。
  • 多 Agent 模式下，每个 Agent 只拿到与任务相关的最小上下文，减少互相干扰。
6.7 自测、整改与 CR
  • 自动运行构建、单元测试、集成测试、Lint、类型检查、安全扫描。
  • 失败日志由测试 Agent 归因，生成修复任务回流给对应编码 Agent。
  • CR Agent 按正确性、设计一致性、可维护性、安全、性能、兼容性打分。
  • 高优先级 CR 问题必须修复或由人工确认豁免，才能进入合并状态。

7. 核心数据对象设计

本章节描述平台需要管理的逻辑数据对象，用于说明阶段流转、审计追溯、Agent 编排和质量门禁需要保存哪些关键信息；这些对象不等同于最终物理数据库表，具体字段类型、索引、主外键和 DDL 应在详细设计阶段再确定。

9. 失败恢复与回滚设计

平台必须默认假设 AI、测试环境、依赖安装、外部服务和人工审批都会失败。失败恢复设计的目标是让任何阶段都能清楚地停住、说明原因、恢复现场，并在审批后继续、重试、回退或取消。

失败分类

类型 典型场景 处理策略
AI 输出失败 结构化输出不符合 Schema、引用不存在、回答自相矛盾 自动重试一次，仍失败则进入人工接管；保留失败输出和模型参数。
阶段门禁失败 反思 Agent 发现阻断问题，或人工评审驳回方案/设计 回到对应生成阶段，带上驳回意见重新生成，禁止跳过阻断项。
代码执行失败 构建失败、测试失败、依赖安装失败、沙箱超时 归因后生成修复任务；环境类失败交给平台运维或人工确认。
集成失败 多 Agent Patch 冲突、接口契约不一致、共享模型变更冲突 冻结集成分支，回滚冲突 Patch，交由集成 Agent 重新排序合并。
业务变更 业务撤回需求、澄清答案变化、验收标准变化 创建新需求版本，触发影响分析，已完成代码进入待确认或回滚状态。

回滚原则

  • 阶段回滚和代码回滚分开处理：阶段可以回退到方案或详细设计，代码可以回滚到指定分支快照。
  • 所有回滚必须写入 rollback_records，包含原因、审批人、影响范围和反向 Patch。
  • 已合并到集成分支的变更必须通过反向 Patch 或新修复提交处理，不能直接删除历史。
  • 涉及数据迁移的任务必须提前生成回滚脚本、兼容读写策略和数据校验脚本。
  • 人工接管后，AI 只能读取人工修改后的最新快照，不能继续基于旧上下文生成代码。

恢复流程

任务失败
  → 记录失败上下文：输入、输出、日志、模型参数、代码快照
  → 失败分类：AI / 门禁 / 环境 / 代码 / 集成 / 业务变更
  → 判断是否可自动重试
      是：按重试策略重新执行
      否：进入 WAITING_HUMAN_APPROVAL
  → 人工选择：继续 / 重试 / 回退 / 接管 / 取消
  → 写入 audit_logs 和 rollback_records

10. 多 Agent 并发控制设计

多 Agent 的效率来自并行，但风险也来自并行。平台需要在任务分配前预测影响面，在开发过程中控制租约，在集成前做冲突预检，避免多个 Agent 分别写出“局部正确、整体冲突”的代码。

并发控制层级

层级 控制方式 适用场景
文件级租约 同一文件同一时间只允许一个编码 Agent 写入 业务服务、配置文件、迁移脚本、测试文件
模块级租约 对高耦合模块设置 owner_agent，其他 Agent 只能只读引用 订单、支付、权限、核心数据模型
接口契约锁 接口入参、出参、错误码、事件格式变更必须先由集成 Agent 批准 跨服务、前后端联动、开放 API
数据模型锁 表结构、枚举、状态机、消息结构由专门任务统一修改 数据库迁移、领域模型、状态流转

任务分配规则

  • 任务 DAG 生成后，先计算每个任务的文件影响面、模块影响面和接口影响面。
  • 如果两个任务会修改同一核心文件，默认串行；只有明确互不影响时才允许并行。
  • 每个 Agent 领取任务前必须申请租约，租约超时自动释放，但释放前要保存当前 Patch。
  • 集成 Agent 按依赖顺序合并 Patch：数据模型和接口契约优先，业务逻辑其次，测试和文档最后。
  • 集成前必须运行语义冲突检查：同一函数重复修改、接口定义不一致、测试期望冲突、配置覆盖。

冲突处理策略

检测到冲突
  → 判断冲突类型：文本冲突 / 语义冲突 / 接口冲突 / 数据冲突
  → 冻结相关 Agent 的继续写入权限
  → 集成 Agent 生成冲突说明和推荐解决方案
  → 必要时回流给原编码 Agent 修改
  → 重新运行局部测试和集成测试
  → 释放租约并继续合并

11. 沙箱执行安全设计

平台会执行用户上传的项目代码，因此沙箱不是附属能力，而是核心安全边界。所有构建、测试、Lint、扫描和脚本执行必须在受控 Runner 中完成。

沙箱策略

策略 要求 说明
资源限制 限制 CPU、内存、磁盘、进程数、执行时长 避免构建脚本拖垮 Runner 或导致任务堆积。
网络限制 默认禁止访问内网、云元数据地址和未知外网地址 依赖下载必须通过白名单代理或企业私有仓库。
凭证隔离 构建凭证按任务临时注入，任务结束立即销毁 禁止把平台密钥、用户密钥或仓库 Token 传入 AI 上下文。
镜像治理 使用可信基础镜像，镜像定期扫描漏洞 不同语言栈准备标准镜像，减少动态安装成本和供应链风险。
文件系统 工作区独立挂载，禁止访问宿主机敏感路径 任务完成后保留必要日志、报告和 Patch，清理临时文件。
脚本审计 执行前扫描危险命令、外联地址、密钥读取、删除操作 高风险脚本进入人工确认或受限执行模式。

依赖安装策略

  • 优先使用缓存依赖和企业私有包仓库，减少外网依赖和构建耗时。
  • 锁文件缺失或依赖版本不固定时，反思 Agent 应标记为可复现性风险。
  • 依赖安装失败要区分网络问题、版本问题、权限问题和脚本问题，避免错误回流给编码 Agent。
  • 对高安全项目启用离线依赖镜像，只允许从审核过的软件源安装。

12. 端到端追溯与验收测试设计

平台必须能回答三个问题：为什么要改这段代码、这段代码实现了哪条业务规则、哪些测试证明它是正确的。端到端追溯和验收测试矩阵是避免 AI 代码“看起来对、实际偏题”的关键。

追溯链路

需求文档段落
  → AI 生成的问题
  → 业务澄清答案
  → 方案设计决策
  → 详细设计任务
  → Agent 编码任务
  → 代码 Diff / Commit
  → 单元测试 / 集成测试 / 验收测试
  → CR 结论

验收测试矩阵

来源 测试类型 生成方式 通过条件
业务规则 验收测试 / 单元测试 从需求和澄清答案中抽取 Given-When-Then 场景 核心规则全部有测试覆盖，失败信息可定位到规则。
边界条件 参数化测试 从字段定义、状态机、金额、时间、数量范围生成边界值 边界值、非法值、空值、重复请求均有预期结果。
接口契约 契约测试 / 集成测试 从详细设计的接口入参、出参、错误码生成 前后端或服务间契约一致，兼容性风险已记录。
数据迁移 迁移校验测试 从数据设计生成迁移前后校验 SQL 或脚本 迁移可重复执行、可回滚、数据量和关键字段校验通过。
非功能需求 性能 / 安全 / 稳定性测试 从方案中的风险和非功能指标生成测试任务 达到指标或形成风险豁免记录。

追溯门禁

  • 没有需求或澄清来源的代码变更，需要人工确认是否属于必要技术调整。
  • 高优先级业务规则必须至少关联一个测试用例和一个通过的测试结果。
  • CR 发现的问题必须关联到具体代码变更；修复后要重新关联验证结果。
  • 需求版本变更后，平台自动找出受影响的设计、代码、测试和 CR 结论。

13. 审批与决策治理设计

AI 可以提高研发效率，但不能替代关键责任人。平台需要把“谁确认了什么、为什么允许继续、哪些问题被豁免”记录清楚，避免 AI 自动推进导致责任不清。

审批矩阵

门禁点 默认审批角色 必须人工审批的条件 审批结果
需求可开发性 产品负责人 / 业务确认人 存在业务规则、验收口径、数据口径变更 通过 / 继续澄清 / 驳回需求版本
方案设计 架构师 / 技术负责人 涉及架构、数据模型、跨服务接口、安全或性能风险 通过 / 选择备选方案 / 退回重写
详细设计 模块负责人 / 测试负责人 涉及接口兼容、数据迁移、状态机、测试矩阵 通过 / 补充设计 / 退回方案阶段
高风险代码变更 代码 Owner / 安全负责人 涉及支付、权限、加密、批量数据、外部调用 通过 / 限制范围 / 人工接管
CR 豁免 技术负责人 / 质量负责人 高优先级问题无法立即修复或需延后处理 限时豁免 / 禁止合并 / 转为后续任务
回滚与取消 项目负责人 / 发布负责人 业务变更、集成失败、上线风险不可接受 回退阶段 / 回滚代码 / 取消流程

决策记录要求

  • 每个审批结论必须关联阶段产物、反思报告和证据链。
  • 每个技术选型、业务口径、异常处理策略都应形成 decision_records。
  • 每个豁免都必须有到期时间、复审人和后续处理任务，禁止永久豁免。
  • AI 在后续阶段引用审批结论时，只能引用已生效且未过期的决策记录。

14. AI 上下文治理设计

AI 生成质量很大程度取决于上下文质量。平台应把每次模型调用使用的上下文做成可版本化、可审计、可复现的上下文包，而不是临时拼接一段长 Prompt。

上下文包内容

内容 来源 校验方式
需求片段 需求文档、澄清答案、决策记录 必须包含版本号、段落位置、业务确认状态。
代码上下文 文件检索、符号图、调用链、依赖图 必须绑定仓库快照和索引版本，禁止使用过期索引。
任务约束 方案设计、详细设计、任务 DAG 必须包含输入、输出、验收条件和禁止修改范围。
历史结果 阶段产物、测试报告、CR 结论、失败记录 只引用当前工作流或被明确批准复用的历史记录。
模型配置 Prompt Registry、模型路由、工具权限 保存提示词版本、模型版本、工具列表和输出 Schema。

上下文质量门禁

  • 上下文包生成后先由检索校验器检查引用是否存在、版本是否一致、是否包含无关大文件。
  • 反思 Agent 需要抽查 AI 结论是否真正被上下文支持，而不是只引用了表面相关文件。
  • 需求或代码快照变化后，旧上下文包自动失效，必须重新生成。
  • 涉及敏感信息的上下文片段必须脱敏，并记录脱敏规则。

15. 合并与交付门禁设计

AI 生成代码不应绕过团队已有的工程纪律。最终变更必须以标准 PR/MR 形式进入仓库，经过 CI、CR、审批和可追溯检查后才能合并。

合并前检查

  • 所有阻断级测试通过，包括构建、单测、集成测试、契约测试和必要的验收测试。
  • 所有高优先级 CR 问题已修复，或存在未过期的审批豁免记录。
  • 所有高优先级业务规则至少关联一个测试用例和通过结果。
  • 最终 Diff 与详细设计任务一一对应，没有无来源代码变更。
  • 合并请求必须包含变更摘要、风险说明、回滚方式和测试报告链接。

合并策略

策略 适用场景 要求
Squash Merge AI 多次修复、提交历史较碎 提交说明必须包含需求、设计、测试和 CR 链接。
Merge Commit 多 Agent 分支需要保留上下文 每个 Agent 分支必须有任务说明和测试结果。
Rebase Merge 小范围线性变更 必须重新运行受影响测试，避免基线变化引入问题。

交付产物

  • 最终 PR/MR 链接、提交 SHA、变更摘要、影响范围。
  • 测试报告、验收测试矩阵、CR 报告、豁免记录。
  • 发布说明草稿、回滚说明、数据迁移说明。

16. 项目环境声明设计

为了让 AI 编码、自测和沙箱执行可复现，每个项目都应维护一份平台可识别的环境声明。平台可以自动推断初稿，但必须允许人工确认。

声明文件示例

version: 1
project:
  name: order-service
runtime:
  language: java
  version: "21"
  package_manager: maven
commands:
  install: "mvn -q -DskipTests dependency:go-offline"
  build: "mvn -q package"
  unit_test: "mvn -q test"
  integration_test: "mvn -q verify -Pintegration"
sandbox:
  cpu: "4"
  memory: "8Gi"
  timeout_minutes: 30
network:
  mode: allowlist
  allowed_hosts:
    - repo.company.local
    - packages.company.local
environment:
  required:
    - DB_URL
    - REDIS_URL
  secret_policy: inject_at_runtime
services:
  mocks:
    - name: payment-api
      type: wiremock
      port: 18080

环境声明规则

  • 平台导入项目后自动推断声明文件，并由项目负责人确认。
  • 缺少锁文件、版本号或测试命令时，需求不得直接进入代码阶段。
  • 环境变量只保存名称和用途，密钥值由密钥服务运行时注入。
  • 外部服务必须声明真实连接、Mock 或禁用策略，避免测试阶段卡死。

17. 可观测性与告警设计

平台需要能被运营和排障。除了业务质量指标，还要监控 AI 调用、队列、沙箱、索引、成本和阶段流转，及时发现雪崩、积压、成本异常和质量下降。

SLO 与告警

指标 告警条件 处理动作
队列积压 等待任务数或等待时间超过阈值 扩容 Worker，限制新任务，提示用户排队状态。
模型失败率 超时、Schema 失败、工具调用失败持续升高 切换备用模型，降低并发，触发 Prompt 回滚。
沙箱失败率 非代码原因导致的构建/测试失败升高 检查镜像、依赖仓库、网络代理和 Runner 资源。
成本异常 单项目或单阶段 Token/模型费用超过预算 暂停自动重试，切换轻量模型，要求人工确认。
质量下降 阶段返工率、CR 高危问题数、测试失败率上升 进入质量保护模式，提高门禁要求，抽检上下文包。
索引滞后 代码快照版本高于索引版本超过阈值 禁止基于旧索引生成代码，优先调度索引任务。

排障视图

  • 工作流时间线：展示每个阶段的输入、输出、模型、耗时、审批和失败记录。
  • Agent 任务视图：展示任务 DAG、租约、上下文包、Patch、测试和重试记录。
  • 成本视图：按租户、项目、阶段、模型统计调用次数、Token 和费用。
  • 质量视图：展示反思得分、返工率、CR 问题、测试覆盖和验收通过率。

18. 稳定性与效率设计

稳定性设计

  • 长任务全部异步化：AI 分析、索引、测试、构建、代码审查都进入队列，避免接口超时。
  • 任务幂等：每个任务有 idempotency_key，重复提交不会产生重复分支或重复变更。
  • 阶段快照：每次进入新阶段都冻结需求版本、代码快照和上下文引用，保证结果可复现。
  • 模型调用降级：主模型失败或超时后，可切换备用模型；低风险任务可使用更低成本模型。
  • 结构化输出校验：AI 输出必须通过 JSON Schema 或业务规则校验，不合格自动重试或转人工。
  • 沙箱隔离：构建和测试在受限容器中运行，限制 CPU、内存、磁盘、网络和执行时间。
  • 分支隔离：每个 Agent 使用独立工作区，集成前不污染主分支。
  • 恢复能力：工作流引擎记录每一步状态，服务重启后可从最近成功节点恢复。

效率设计

  • 增量索引：代码变更后只重新索引变化文件和受影响符号，避免全量重建。
  • 上下文裁剪：AI 只接收与当前任务相关的文件、符号、需求片段和澄清记录。
  • 缓存策略：文件摘要、依赖图、文档解析结果、嵌入向量、常见问题分类可缓存。
  • 并行执行：多 Agent 任务、测试矩阵、静态扫描可以并行运行，由任务 DAG 控制依赖。
  • 分层模型：需求总结、分类、格式化用轻量模型；架构设计、复杂编码、CR 用强模型。
  • 提前失败：进入代码阶段前先检查构建命令、依赖安装、测试环境，避免写完代码才发现环境不可用。
  • 局部验证：小任务先运行相关测试，最终集成后再运行全量测试。

质量指标

指标 目标 采集方式
需求澄清命中率 AI 提出的问题中，被业务确认有效的问题占比 业务反馈标记、问题关闭原因
阶段返工率 进入后续阶段后回退到前置阶段的比例 工作流状态流转日志
代码一次通过率 AI 首次提交后通过构建和关键测试的比例 test_runs
CR 高危问题数 每次变更中的阻断级缺陷数量 review_findings
上下文引用准确率 AI 结论引用的文档或代码证据是否真实匹配 反思 Agent 抽检、人工标注
端到端耗时 从需求上传到可合并代码的总时长 workflow_runs

19. 安全与权限设计

  • 租户隔离：项目、文档、向量索引、对象存储路径按租户隔离。
  • RBAC 权限：管理员、架构师、开发、测试、业务确认人、只读访客分别授权。
  • 密钥保护：上传项目后自动扫描密钥，敏感值脱敏，禁止传入模型上下文。
  • 提示词注入防护：需求文档和代码注释都视为不可信输入，AI 系统指令和工具权限必须隔离。
  • 代码执行隔离：沙箱默认禁止访问内网和云元数据地址，需要外网依赖时走白名单代理。
  • 审计追踪：用户确认、AI 决策、代码修改、测试执行、CR 豁免都要写入审计日志。
  • 数据保留策略：支持项目归档、按租户删除、模型日志脱敏、向量索引清理。
  • 合规控制：对金融、医疗、政企等场景可启用私有化模型、私有对象存储和内网部署。

20. 部署方案

逻辑服务拆分

服务 职责 扩展方式
web-console 前端工作台，代码编辑、需求、流程、CR 页面 CDN 或静态资源横向扩展
api-gateway 鉴权、限流、接口聚合、租户识别 无状态横向扩展
workflow-service 阶段状态机、人工确认、任务调度 按工作流分片，依赖队列削峰
ai-orchestrator Agent 编排、模型调用、上下文组装、输出校验 按任务队列横向扩展，配置模型限流
repo-service Git 操作、文件读写、分支、Diff、提交 按项目工作区分片，使用共享对象存储
index-service 代码索引、文档索引、向量检索 CPU 型任务可并行，索引结果缓存
sandbox-runner 构建、测试、Lint、扫描 Kubernetes Job 或独立 Runner 池
notification-service 事件通知、SSE/WebSocket、邮件/IM 推送 按连接数横向扩展

推荐环境

  • 开发环境：单机 Docker Compose，便于快速迭代。
  • 测试环境：Kubernetes + 独立 Runner 池，验证多任务并发和沙箱隔离。
  • 生产环境：Kubernetes 多副本部署，数据库主从或云托管，Redis 集群，S3/MinIO 对象存储，集中日志和指标。

21. 实施路线

阶段 周期建议 交付内容 验收标准
MVP 1：项目工作台 3-5 周 项目上传、文件树、代码查看、编辑、Diff、基础 Git 分支 能导入真实项目并完成一次人工编辑与提交
MVP 2：需求澄清闭环 3-4 周 文档上传、需求分析、问题生成、业务反馈录入、多轮澄清、反思报告 AI 能基于项目代码提出有效澄清问题，并判断是否可开发
MVP 3：方案与详细设计 3-4 周 方案生成、Agent 策略判断、详细设计文档、任务 DAG 详细设计能明确到文件、接口、数据、测试场景
MVP 4：代码编写与自测 4-6 周 单 Agent 编码、Patch 生成、测试运行、失败回流修复 能对中小需求完成端到端代码修改并通过测试
MVP 5：多 Agent 与 CR 4-6 周 任务拆分、多 Agent 并行、集成、代码审查、优化回流 复杂需求可拆分并行开发，CR 阻断问题可闭环修复
增强阶段 持续迭代 知识库、模型评估、成本控制、私有化部署、企业权限、插件市场 达到企业级稳定性、安全性和可运营能力
落地建议： 第一版不要同时追求所有能力。优先打通“项目上传 - 需求问题生成 - 澄清循环 - 方案/详细设计 - 单 Agent 修改代码 - 测试 - CR”的最小闭环。闭环跑通后，再增强多 Agent、复杂索引、企业级安全和高级质量度量。
